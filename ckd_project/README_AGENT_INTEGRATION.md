# CKD Care — Agent Integration (UI preserved)

This bundle keeps the existing React UI and adds the agent pipeline to the FastAPI/MySQL backend. It includes the original source tree, a trained model artifact created from the included `data/processed/ml_dataset.csv`, and a database migration for saved analysis results.

## Agents included

1. **Data Validator** — checks visit dates and eGFR values, and records data-quality issues.
2. **eGFR Calculator** — calculates a missing eGFR only when age, gender code (1=male / 2=female), and serum creatinine in mg/dL are available; uses the 2021 CKD-EPI creatinine equation. It marks stored calculated values with `data_source='CALCULATED'`.
3. **Trend Analyzer** — estimates the annualized eGFR slope from dated measurements; it does not infer a slope from a single visit.
4. **Progression Predictor** — uses `models/trained/ckd_model.joblib`; if model loading/scoring fails, a transparent trend-based screening fallback is returned without fabricating a probability.
5. **SHAP Explainer** — attempts to return top feature contributions for a compatible trained model; explanation failure does not crash the whole pipeline.
6. **Prioritization Agent** — creates a review queue priority and reasons. This is an operational aid, not a diagnosis or treatment recommendation.
7. **LangGraph Orchestrator** — coordinates the steps. A sequential fallback is present for environments where LangGraph is not installed, while LangGraph is used when available.

## Important model limitation

The joblib model was trained on the included processed cohort (2,072 rows; target column `rapid_progression`). A simple random holdout test produced ROC-AUC approximately 0.61. At a 0.30 probability threshold, the model is intended as a prototype screening aid, not a clinically validated predictor. The label definition and possible relationship between `egfr_slope_ours` and the target must be reviewed before any clinical use. The model must not be used to make autonomous treatment decisions.

## Windows setup

1. Extract this ZIP to a normal writable folder.
2. Install Python 3.11 or 3.12 recommended for dependency compatibility.
3. Create and activate a virtual environment in the project root:

   ```powershell
   py -3.12 -m venv .venv
   .\.venv\Scripts\Activate.ps1
   python -m pip install --upgrade pip
   pip install -r backend\requirements.txt -r backend\requirements-rag.txt
   ```

4. Create a MySQL database named `ckd_project` and configure credentials in `.env`:

   ```sql
   CREATE DATABASE ckd_project CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   ```

   Copy `.env.example` to `.env`, then replace the database user/password and JWT secret. Do not commit `.env`.

5. Run the existing project database migrations/setup SQL that your database already requires. Then execute `CKD_Agent_Integration_Migration.sql` in the `ckd_project` database. This adds only the new `patient_analyses` table; existing patient records are not changed.
6. Start the backend from the project root:

   ```powershell
   python -m uvicorn backend.app:app --reload --port 8000
   ```

7. In another terminal:

   ```powershell
   cd frontend
   npm install
   npm run dev
   ```

   Open the URL printed by Vite (normally `http://localhost:5173`). The frontend source and styles have not been modified for this integration.

## Analysis behavior

- Adding a visit saves it first, calculates eGFR if possible, then runs and saves the agent analysis. If analysis fails, the visit remains saved and the response reports analysis status.
- To rerun analysis, send an authenticated `POST /patients/{patient_id}/analyze` request as an Admin or Doctor.
- `POST /predict` remains available for the legacy request-body workflow.
- The saved result is returned in each patient record under `latest_analysis` and stored in `patient_analyses`.
- Blank patient IDs are generated by the API as `CKD-000001`, `CKD-000002`, etc. Existing IDs are preserved. The existing UI layout is unchanged; its current Patient ID field remains as-is, and the API supports omitted/blank IDs for clients that permit them.

## Clinical and data safety

This is an academic prototype. eGFR estimates require correct units and demographic coding; calculated values need clinician verification. A single eGFR value cannot establish a progression trend. The ML output, SHAP factors, and prioritization are not a diagnosis, do not replace clinical judgment, and must not be used for autonomous clinical decisions. Use synthetic/de-identified data during development.


## Latest integration changes

- The existing patient profile now has a Doctor/Admin-only **Assess patient** action that calls `POST /patients/{patient_id}/analyze`.
- New patients receive a generated `CKD-xxxxxx` Patient ID and a generated source identifier (`<source_code>-SRC-xxxxxx`) if those values are omitted. Existing records and IDs are not rewritten.
- eGFR calculation is invoked from within the Data Validation Agent helper; it is no longer a separate LangGraph node. The graph then runs validation, trend analysis, progression prediction, SHAP explanation, and prioritization.
- The existing UI layout and CSS were preserved; only the add-patient identifier inputs and profile action were adjusted.
